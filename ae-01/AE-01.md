## Step 1 — Where this fits (AE-00 big picture)

```text
Create Context → Publish & Connect in UC → Build Agent → Quality → Publish
└──────────────────────────── all of it lives in a GitLab repo ────────────────────────────┘
                     every change goes through: branch → MR → pipeline → review → merge
```

The GitLab repo is the **source of truth** for everything that isn't data:
the pipeline code for context, the UC function definitions, agent code, prompts, eval datasets, and deployment config.

A typical enterprise agent repo (you'll grow toward this over the AE modules):

```text
agent-project/
├── .gitlab-ci.yml          ← the pipeline (MUST be at repo root)
├── databricks.yml          ← Databricks Asset Bundle: what to deploy where (dev/staging/prod)
├── src/
│   ├── context/            ← AE-02: bronze → silver → chunks → vector index jobs
│   ├── tools/              ← AE-04: functions the agent can call
│   └── agents/             ← AE-05..07: agent graphs, A2A services
├── prompts/                ← prompts versioned like code
├── evals/                  ← AE-08: golden datasets + eval scripts
├── tests/                  ← unit tests for tools
├── requirements.txt        ← pinned dependencies
└── .env.example            ← names of required env vars, fake values only
```

**JS comparison:** `.gitlab-ci.yml` ≈ a GitHub Actions workflow, and the jobs ≈ `npm run lint && npm test` running on a fresh machine for every push.

> **Ref:** [Anthropic — Building effective agents](https://www.anthropic.com/engineering/building-effective-agents) (read "workflows vs agents" only for now)

## Step 2 — The merge request (MR) flow

GitLab says **merge request (MR)**; GitHub says pull request (PR). Same idea.

```text
1. git switch -c feat/severity-tool          ← branch from main
2. code + commit (small commits, clear messages)
3. git push → open MR into main              ← (real project only — we don't push in this repo)
4. Pipeline runs on the MR: lint → test → eval
5. Reviewer reads diff + pipeline result + eval report artifact
6. Approve → merge → pipeline runs again on main → deploy job (dev/staging)
```

Things you'd see in GitLab that the mini runner imitates:

| GitLab UI | Mini runner |
|---|---|
| Pipeline graph on the MR (green/red per job) | `Pipeline summary` table |
| Job log | The printed output of each job |
| Settings → CI/CD → Variables (masked) | `export NAME=...` in your terminal; values with TOKEN/SECRET/KEY/PASSWORD in the name are shown as `[MASKED]` |
| "Download artifacts" button | the `eval_report.json` file left on disk |
| `merge_request_event` vs `push` pipelines | `--source merge_request_event` / `--source push` |

What the mini runner does **not** do: Docker images, parallel jobs, `needs`, `include`, caches, protected branches, approvals.

> **Ref:** [GitLab — Merge requests](https://docs.gitlab.com/user/project/merge_requests/)

```bash
DATABRICKS_HOST=https://fake.example.com DATABRICKS_TOKEN=FAKE-TOKEN-FOR-TESTING-123456 python ae-01/03_config_and_secrets.py
```

**Unit test vs eval (important for agents):**

| | Unit test | Eval |
|---|---|---|
| Question | Does the code do exactly what I wrote? | Is the output good enough on realistic cases? |
| Result | pass/fail per test | a **score** (e.g. 0.92) compared to a threshold |
| Deterministic? | yes | with LLMs, no — answers vary between runs |
| Example | `classify_severity(110) == "high"` | "90% of golden questions answered correctly and grounded" |

Agents need both. The eval gate is how a team stops a prompt change from silently making the agent worse.

## Step 4 — What this looks like in the real project (Databricks + GitLab)

You can't do these, but this is what you'd do on the job:

1. **Clone** the team repo from GitLab, create a branch, run tests locally.
2. **Secrets:** a maintainer adds `DATABRICKS_HOST` and `DATABRICKS_TOKEN` (or OAuth credentials for a **service principal**) under *Settings → CI/CD → Variables*, marked **masked** (hidden in logs) and **protected** (only available on protected branches like `main`). You never see or paste the production token.
3. **MR pipeline:** lint + unit tests + eval run on every MR. The eval job may call a Databricks model serving endpoint, so it needs those variables.
4. **Deploy job** on `main`, usually with the Databricks CLI and an Asset Bundle:
   ```yaml
   deploy-dev:
     stage: deploy
     script:
       - databricks bundle validate -t dev
       - databricks bundle deploy -t dev
     rules:
       - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
   ```
   That reads `databricks.yml` and creates/updates jobs (e.g. the AE-02 context pipeline) and apps in the Databricks workspace.
5. **Promotion:** dev → staging → prod are separate targets in `databricks.yml`. Prod deploys are usually manual (`when: manual`) and need approval.

> **Refs:**
> - [GitLab — CI/CD variables (masked/protected)](https://docs.gitlab.com/ci/variables/)
> - [Databricks Asset Bundles](https://docs.databricks.com/aws/en/dev-tools/bundles/)

### Exercise 2 — Write a secret scanner (`ae-01/check_secrets.py`)

A small security job that many enterprise pipelines have.

Requirements:
1. Takes one or more folder paths as arguments: `python ae-01/check_secrets.py lc-01 ae-01`
2. Scans every `.py`, `.yml`, `.yaml` file inside them (recursively)
3. Flags lines that look like a hardcoded secret: a name containing `key`, `token`, `secret` or `password` (any case) **assigned a quoted string literal**, e.g. `api_key = "abc123"` or `TOKEN: "abc"`

## Python / YAML patterns you will see today (quick reference)

| Pattern | What it means | JS equivalent |
|---|---|---|
| `os.environ.get("X", "default")` | Read env var with a fallback | `process.env.X ?? "default"` |
| `sys.exit(1)` | Exit with failure code | `process.exit(1)` |
| `sys.argv[1:]` | Command-line args (without script name) | `process.argv.slice(2)` |
| `argparse.ArgumentParser` | Proper CLI flags (`--source`) | `yargs` / `commander` |
| `subprocess.run([...])` | Run a shell command | `child_process.spawnSync` |
| `Path(__file__).resolve().parent` | Folder of this file | `path.dirname(fileURLToPath(import.meta.url))` |
| `path.rglob("*.py")` | Recursive file search | `glob("**/*.py")` |
| `yaml.safe_load(text)` | YAML → dict/list | `yaml.parse(text)` |
| `class TestX(unittest.TestCase)` | Test suite | `describe(...)` |
| `self.assertEqual(a, b)` | Assertion | `expect(a).toBe(b)` |
| `{k: v for k, v in d.items()}` | Dict comprehension | `Object.fromEntries(Object.entries(d).map(...))` |
| YAML `- item` | List element | `[item]` |
| YAML indentation | Nesting (spaces only, no tabs) | `{ }` |
